# 04 · 智能体实现

> 本文回答三件事：这个系统为什么是智能体、循环跑在哪里、确定性判断为什么不在模型手里。
> 与 [`02-架构设计.md`](02-架构设计.md) 冲突时，以本文为准（02 写作时模型网关还假设在服务端）。

---

## 一、为什么是智能体，而不是「套了模型的表单」

判据只有一条：**把模型拿掉，流程还能不能跑。**

| 环节 | 旧实现（demo 版） | 现实现 |
|---|---|---|
| 下一步做什么 | 前端写死 `questionBank[idx++]` | 模型每轮自己决定（先读状态？先锁岗？该追问还是换层？） |
| 分数从哪来 | JavaScript 里 `2 + bullets * 1.5` | 模型给证据 → 服务端量规算分 → 模型不得自行报总分 |
| 失败怎么办 | 不存在的分支 | 工具返回 `ok:false` 与 `error`，模型改参数重试，两次仍失败就如实告知 |
| 状态 | localStorage 里的一段 JSON | 服务端 session，S0–S5 状态机；状态摘要与事实清单随每轮指令下发（§十.3），模型只在缺字段时查 `get_context` |

模型是调度器，不是计算器。**能算的交给工具，要解释的交给模型**（沿用 02 §1.1）。

## 二、运行形态：循环在端侧，工具在服务端

```
┌──────────────── 浏览器（web-v1） ────────────────┐
│  agent.js                                        │
│  ┌────────────────────────────────────────────┐  │
│  │ while 未收敛:                               │  │
│  │   LLM(系统指令 + 状态 + 工具表)  ──流式──▶ UI │  │
│  │   ├ 只出文本 → 结束                         │  │
│  │   └ 出 tool_calls → 执行 → 结果回灌 → 继续  │  │
│  └────────────────────────────────────────────┘  │
└──────────┬───────────────────────────┬───────────┘
           │ 云模型（keyless, 直连）    │ /api/agent/*
           ▼                           ▼
   云服务 LLM API            FastAPI（server/）
                             工具 9 个 · 量规 · session
```

**为什么循环不在服务端**：平台云模型是 keyless、仅流式、按应用 Origin 校验的端侧通道，且明确禁止服务端代理（BFF）。所以模型调用只能发生在页面里，服务端负责它拿不到的东西——确定性计算与持久状态。

代价与收益：浏览器多跑一个循环（成本几乎为零）；换来零密钥、无跨域代理、工具可单测。

## 三、循环长什么样

`web-v1/agent.js` 的核心不到 40 行：

```js
const plan = await prepare({ module, resume, target_role });  // 存档 + 锁岗：确定性准备，开场即完成
const messages = [{ role: "system", content: plan.system }, ...history, { role: "user", content: userText }];

for (let round = 0; round < maxRounds; round++) {
  const step = await streamChat({ messages, tools: plan.tools });   // 流式，工具分片按 index 归并
  if (!step.toolCalls.length) return step.content;                  // 收敛
  messages.push({ role: "assistant", content: step.content, tool_calls: step.toolCalls });
  for (const call of step.toolCalls) {
    const payload = await callTool(call.function.name, parseArgs(call));   // 服务端执行
    deriveEvents(call.function.name, payload, emit);                       // 工具结果直接驱动界面
    messages.push({ role: "tool", tool_call_id: call.id, content: JSON.stringify(payload) });
  }
}
```

三条纪律：

1. **工具表按模块下发**，诊断 7 个、面试 3 个、复盘 3 个。不把九个工具一次性塞给模型。
2. **界面由工具调用驱动**，不靠解析模型的话。模型说「我给你打了 6 分」不算数，`score_career` 返回的 `total` 才算数——所以雷达图能跟着工具结果更新。
3. **每轮重取系统指令**，把服务端状态拼在末尾。模型不需要「记住」岗位与轮次，它每次都重新读到。

外加一条工程纪律：**没有判断空间的动作不要占模型的一轮往返**。`save_resume`（字段填进去）和 `lock_jd`（岗位记下来）都不需要模型决策，所以诊断入口改用 `POST /api/agent/prepare` 在对话开始前做完，并把结果直接写进状态摘要（`has_resume` / `jd_locked` 一进来就是 true）。模型第一轮就能判分，界面少等一轮模型往返。判分、找证据、建清单这些真正需要判断的动作仍然只能由模型发起——否则就不叫智能体了。

幂等由指纹保证：简历的规范化指纹相同就不重复存档（不会把已算好的分数冲掉），岗位 + JD 相同就不重复锁岗。

## 四、九个工具

| 工具 | 谁在用它 | 为什么必须是代码 |
|---|---|---|
| `get_context` | 全部（按需） | 状态是唯一真本，不能靠对话记忆；摘要与清单已随指令下发，只在缺字段或要复核逐题记录时调用 |
| `save_resume` | 诊断 | 五类字段校验、版本号自增、旧分数旧清单失效 |
| `lock_jd` | 诊断 | 技能重合率 → 专业基础分的映射表写死（03 §3.3） |
| `score_career` | 诊断 | 权重算总分、等级判定、两次诊断波动 >5 分自动标记不稳定；简历缺模块时按 `missing` 上报（服务端核对确实缺才收）；`fallback` 由服务端规则兜底（上限 6 分，见 10.5） |
| `build_fact_sheet` | 诊断 | E1…En 编号一次生成不再变；证据强度按「有没有数字 + 角色词」判，不靠模型自评；`auto` 从简历要点摊条目（兜底用） |
| `validate_rewrite` | 诊断 / 面试 | 改写前后实体比对，数字只减不增，角色词不得升级（03 §3.5） |
| `log_interview_turn` | 面试 | 一题多问拦截（正则数问号）、同层连续两轮回退、轮次上限、fact_id 必须在清单内 |
| `save_report` | 复盘 | 四栏缺一即拒收；面试五维加权总分与结论等级由服务端算 |
| `export_resume_docx` | 诊断 / 复盘 | python-docx 生成，30 分钟有效的下载令牌 |

拒绝是设计的一部分。下面这些都会真的被拒：

```
score_career  → {"ok": false, "error": "以下低于 7 分的维度没有给出扣分证据：output、collaboration"}
log_interview_turn → {"ok": false, "error": "fact_id 必须是清单内的编号：E1、E2"}
save_report   → {"ok": false, "error": "qid=Q1 缺字段：gap（四栏缺一即不合格）"}
validate_rewrite → {"ok": false, "violations": ["改写新增了原文没有的数字：180ms、65ms",
                                                "改写把角色改成「主导」，原文未出现该表述"]}
```

模型拿到这些错误后自己改参数重试——这才是「智能体」和「一次问答」的区别。

## 五、状态机与权限

沿用 [`03-逻辑梳理.md`](03-逻辑梳理.md) §二，但现在由服务端强制：

| 状态 | 触发 | 越权后果 |
|---|---|---|
| S0 → S1 | `save_resume` | 五类字段全空时 `can_diagnose: false` |
| S1 → S2 | `score_career` | 没存档就打分 → 直接拒 |
| S2 → S3 | `build_fact_sheet` | 没出分就建清单 → 直接拒 |
| S3 → S4 | `log_interview_turn` | 清单为空就出题 → 直接拒 |
| S4 → S5 | `save_report` | 没有答题记录就复盘 → 直接拒 |

前端只做一件事：把 `stage` 显示出来，让用户知道卡在哪一步。

pip install -r requirements.txt

## 七、验证记录（本地实测）

| 场景 | 结果 |
|---|---|
| 工具链：存档→锁岗→打分→清单→改写校验→导出 | 全部通过；缺证据被打回一次，补证据后 `total=44` |
| 面试规则 | `fact_id=E9` 被拒；两个问号触发「一题多问」；同层第二轮触发换层提示 |
| 复盘 | 无答题记录被拒；四栏缺 `gap` 被拒；补全后 `total=54 · 有潜力` |
| 端侧循环（假模型注入） | 工具分片跨 chunk 归并成功 → 执行 → 事件派发 `scores:44` → 流式文本 → 结束 |

### 真模型下的联调修正（发布域名实测）

| 现象 | 根因 | 修法 |
|---|---|---|
| 发布域名接口请求超时 | 端侧把 API 拼成 `域名:8000` | 同源优先：非本地环境一律走相对路径 |
| 页面加载云 SDK 失败 | jsdelivr 在用户网络不可达 | SDK 收进 `web-v1/vendor/`，不依赖外网 CDN |
| 网关偶发 5xx 整轮作废 | 只对白名单错误重试 | 改为「未吐字就重试」，仅 `auth_/quota_/400` 类确定性错误放弃 |
| 答完题下一题出不来 | 出题轮拿到题目后仍在空转，用户答题被 `busy` 挡 | 出题任务加早停（`stopOn: question`）+ 答题期间禁用发送 |
| 面试反馈里夹带「改写校验未通过」 | 面试模块下发了 `validate_rewrite`，模型顺手去改简历 | 面试工具集收窄为 `get_context` + `log_interview_turn`，指令里加「本轮不改简历」 |
| 同一条目同层换句话重问 | 同层只给 warning，模型可以无视 | 同 `fact_id` + 同 `layer` 第二次直接拒；换条目则层数重新计数 |
| 只答 1–2 题也能报 72 分 | 模型自评偏松 | 服务端按样本量封顶（1 题≤4 分/维、2 题≤6 分/维），返回 `capped`/`confidence`，指令要求如实说明 |
| 迁移后本机 PIN 登录异常 | `HiberbootEnabled=1`（快速启动）导致重启后身份提供程序未初始化 | 与项目无关；建议关快速启动或重设 PIN |
| 诊断期间界面近 55 秒只有一行小字，像卡死 | ① 首轮要等模型先调 `save_resume`/`lock_jd` 才轮到打分；② 模型这轮的话只进了流缓冲区，界面没渲染；③ 总分位只剩一个省略号 | ① 新增 `POST /api/agent/prepare`，存档与锁岗在对话前做完（幂等），模型开场直接判分；② 流式文字贴到提示区；③ 总分位改「分析中 + 转圈」、维度条骨架、雷达占位 |

## 八、还欠的三件事

## 九、知识库（`server/kb/`）

### 9.1 形态与链路

知识以**结构化 JSON** 存在项目里，随应用一起部署，运行时只读，不依赖任何外部服务。

```
桌面 md（人写）  ──python server/kb/build.py──▶  server/kb/*.json  ──knowledge.py──▶  提示词 / 工具
```

| 文件 | 内容 | 接在哪 |
|---|---|---|
| `roles.json` | 岗位 → 必备技能 / 加分技能 / 考察重点 / 常见不足 | `lock_jd` 无 JD 时算重合率；`agent.py` 注入考察重点 |
| `questions.json` | 岗位 × 五层追问题库 | 面试轮注入当前层 5 条候选 |
| `anchors.json` | 五维 × 5 档行为锚点 + 41 条判分提示 | 诊断轮注入判分口径 |
| `writing.json` | 弱动词 / 强动词 / 量化四类 / 反例对照 | 诊断轮注入；`validate_rewrite` 返回 `warnings`/`asks` |

源 md 覆盖 6 个岗位（后端、前端、数据分析、产品、测试、算法）、132 道题。新增 md 后重跑 `build.py` 即可，代码不用改。

### 9.2 两个容易踩的坑

**① 无 JD ≠ 没有基准。** 早先 `lock_jd` 在没拿到 JD 时返回 `required: []` → 重合率 0 → 专业基础恒为 3 分（模型最多调到 4）。前端又把 JD 写死为空串，等于每条线上诊断都被系统性地压掉约 5 分。现在无 JD 时按岗位名查 `roles.json` 的必备技能算重合率；岗位不在库（如硬件工程师）才回落 3 分，并明确返回 `source: "no-baseline"` 让模型如实说明缺基准。

**② 能力描述型条目要派生别名。** 题库里的必备项有两种写法：具体技术名（Java、PyTorch）和能力描述（方向经验、模型训练与效果评估）。学生简历的技能清单只出现前者，后者永远匹配不上，等于每份简历白扣几项。`build.py` 因此做一层机械归一：条目名按「与/和/、」拆子概念、说明里的英文技术名收作别名。只切分不新增语义，别名不改进提示词，只影响匹配。

### 9.3 已知边界（如实记）

- **两项算法岗必备项无法由技能清单核验**：「模型训练与效果评估」「数学基础」是能力判断，简历技能清单里没有对应词。因此算法岗基础分最高约 7（模型可上下调 1），不会给到 9。
- **题库来源边界**：只取框架与考察点，不搬他人题库原文，也不搬「岗位管理」库里禁抓正文的说明书。
- **来源标注**：`roles.json` 每条带 `src` 字段记录 JD 出处，只做溯源，不进提示词。

## 十、两个「假数据」缺陷的收尾

演示期有两处一直用写死的假数据顶着，一旦让学生用真实简历就会露出来。已改掉。

### 10.1 粘贴的简历要真的进入诊断

**原来的问题**：`#parsePaste` 只检查文本框非空，随后加载一份写死的示例简历（陈亦舟 / 后端开发工程师）。学生贴自己的简历，看到的、被打分的全是别人的内容。

**现在**：`parseResumeText()` 本地确定性解析，不调模型：

| 步骤 | 做法 |
|---|---|
| 切段 | 短行（≤14 字）命中「教育背景 / 实习经历 / 项目经历 / 专业技能 / 证书 / 自我评价」即换段 |
| 基本信息 | 姓名取首行短名词；电话、邮箱走正则；`求职意向：` 优先，其次找含岗位词且不含校名的短句 |
| 教育 | 命中「大学/学院/学校」起一条，抽学校、专业（关键词匹配）、学历、时间、其余进 extra |
| 实习 / 项目 | 非项目符号行当标题，其余行当要点；`技术栈：` `使用` `基于` 抽栈，角色词（负责人 / 独立开发 / 参与者）单独取 |
| 技能 | 按 `、，/ |` 与空格拆词条，滤掉「熟悉 / 掌握 / 精通」这类动词 |

边界写在代码里：`.pdf / .docx` 先交服务端提取文字（`pypdf` / `python-docx`，不经过模型），`.txt / .md` 直读，粘贴文本直接解析；三者进同一套本地解析与同一个编辑器。`.doc` 老格式与图片型扫描件显式拒绝并提示改用粘贴，不再假装解析。解析出的项不足 3 个会直接提示"请按小标题分行"，不静默放行。

`blankResume` 同时去掉了示例姓名与岗位，模板起步不再顶着别人的名字。

### 10.2 证据必须是简历里真实存在的句子

**原来的问题**：模型会把 `{"skills":["Java","Spring Boot"...]}` 这类工具入参片段当成"原文引用"提交，界面上一本正经地显示成扣分依据，实际无法回查。

**现在**：`score_career` 逐条核验 `quote`：

1. **逐字段比对**，不把整份简历拍平——否则技能列表 `["Python","PyTorch"]` 去标点后连成一串也能匹配；
2. **要求像一句话**：归一化后 ≥8 字，且含 ≥2 个汉字（全英文简历放宽到 ≥12 字），挡掉 `TensorFlow` 这种单词引用；
3. 用 `…` 省略的，每段都要落在同一个字段里；
4. 全部不通过 → `ok: false`，并回一个 `example_quote`（从简历里挑的真实句子）让模型照着改；
5. 部分不通过 → 剔除，返回 `rejected_quotes`，前端只渲染服务端核验过的证据（`payload.evidence`，不再用模型参数里的 `args.evidence`）。

### 10.3 三处流程自愈

- **只说话不动手**：诊断轮没产出 `score_career` 就结束（常见于模型跑去问学生补字段），客户端补一次明确指令再执行；只补一次，避免死循环。
- **会话对不上**：工具返回"还没有保存简历"（发布/扩容时请求可能落到另一实例），客户端自动重放 `prepare` 再重试这次工具调用，不让模型自己绕去 `save_resume`。

- **上一轮没结束就点了下一步**：诊断刚出清单时模型还在收尾，此时点「进入面试」原本会被 `busy` 挡掉，界面只显示「本轮没有拿到问题」。现在下一轮会等上一轮收尾再开始，最多等 40 轮。

### 10.4 浏览器里一步都跑不起来的真正原因

现象：内部直连诊断 54 分、证据与清单都正常；同一份代码在浏览器里全部失败，`Failed to fetch`，重试三次无用。

根因在 `conversationId`：SDK 的 `createStreaming` 把它摘出来写进 `X-Conversation-ID` 请求头。这个头不在 CORS 安全清单里，跨源时浏览器必先发预检；网关的 `Allow-Headers` 不含它，预检被拒，请求在浏览器层面就死了，页面只能拿到一句 `Failed to fetch`。

A/B 实测（同一页面、同一模型）：

| 请求 | 结果 |
|---|---|
| 不带 `conversationId` | `ok(chunks=1)` |
| 带 `conversationId` | `Error: Network error: Failed to fetch` |

处理：`conversationId` 只在页面与 `endpoint` 同源时才上送（会话分组是附加能力，跨源就不带）。同时 `init()` 补一次真实的流式探活——`models.list` 能通不代表 `chat` 能通，之前正是这里静默失败，界面一直显示「就绪」。

### 10.5 模型不可用时的降级：兜底也要落库

只在界面上算个 41 分、不写服务端，结果就是 `career_scores` 为空、没有事实清单，面试页永远拒绝——重启多少次都没用。

现在诊断失败会调两个服务端工具：`score_career{fallback:true}`（规则估分，上限 6 分）+ `build_fact_sheet{auto:true}`（从简历要点摊条目）。分数与清单都落在会话里，界面标明「规则估分 · 非模型判断」，`career_source: "rules"` 同时进状态摘要，模型被问到不得复述成自己的判断。兜底刻意不接受前端传来的分数——那等于让浏览器判分入库。

### 10.7 第三轮：状态一致性与「刷新就归零」

前三轮修的是"跑不通"，这一轮修的是"看着通了但状态对不上"。按缺陷逐条列，每条都有可复现的现象。

| 现象 | 根因 | 改法 |
|---|---|---|
| 刷新后简历、当前页面、复盘一起消失 | 读 localStorage 时判断 `saved.basic`，但 `state` 里根本没有这个键（简历在 `saved.resume.basic`），整段持久化一直是空转 | 按 `state` 自己的字段判断（`resume` / `nav` 存在即恢复） |
| 同一会话里的第二场面试一开始就是「第 6 / 5 轮」 | 新清单只清了 `turns`，留下了 `round_no / asked / answered / last_prompt_key` | 新增 `POST /api/agent/session/{id}/interview/start`，由 `reset_interview` 整场清零；点「开始面试」时先调它 |

| 改了简历，专业基础分还是按旧技能算 | `lock_jd` 的 `foundation_score` 依赖简历技能，而 `jd_sig` 只看岗位+JD，改简历不会重算 | 记住 `jd_args`，`save_resume` 后按同口径重算基线 |
| 刷新后进面试要再等一次四十秒诊断 | 分数/证据/清单只在前端内存里 | 启动时先幂等 `prepare`（简历没变不重存），再 `/api/agent/session/{id}` 取回分数、证据、清单；`career_evidence` 因此落库 |

| 诊断刚出清单就点面试，偶尔报「上一轮还没结束」 | 并发那一路把自己的空 promise 写进 `currentTask`，把真正在跑的那轮丢了 | 忙判定与登记之间不留 `await`，登记后只在同一个 promise 上清空 |
| 云模型不可达时页面永久停在「初始化中」 | `probe` 只靠 `AbortSignal`，SDK 不透传就挂死 | 流式首字节与 12 秒死线竞速，超时也一定会返回 |
| 静态服务器（4174）下每个 GET 都多一次预检 | 无 body 的 GET 也带 `Content-Type: application/json` | 只有带 body 才设该头 |
| 首行写「个人简历」时，姓名栏显示成「个人简历」 | 姓名兜底取第一行首段，没有词性校验 | 只接受 2–4 汉字或拉丁名，且不含小节词（简历/求职/教育…） |

### 10.8 第四轮：实测报告里的 11 个问题的修法

对应 `docs/05-待修问题清单.md`。修的是「报错位置」而不是「报错文案」：每条都写到根因那一层，避免下次换个入口再犯。

| 现象 | 根因 | 修法 |
|---|---|---|
| 复盘生成完界面停在「生成中」，刷新才出来 | 上一轮的流式请求没有终点：网关半路不发 `[DONE]` 时 `for await` 永远挂着，`review()` 的 promise 不 settle；`runTask` 又在「循环 40 次 await 同一个 promise」上陪等 | `streamOnce` 加静默看门狗（30s 无 chunk 先 abort 再硬 reject）；`runTask` 改成只等一次且 45s 上限；`agentReview` 三路兜底——`save_report` 一成功就跳（不等模型写收尾话）、75s 硬上限、之后轮询 `session()` 取报告 |
| 对话流留一个空白「AI」气泡 | 先建 bubble 再等文字，断流就剩空壳 | 只有正文非空才把「正在输入」换成气泡；收尾时清掉空 bubble |
| 一题多问不报警，首题就问了四件事 | 只数问号；顿号并列四个疑问也只有一个问号 | `rubric.split_asks` 数疑问词（多少/几张/什么工具/多少并发…）；前两次硬拒并回传 `asks`，第三次起降级为警告（不许把 maxRounds 耗光） |
| 诊断页「最该先改的三件事」空白 | `top_gaps_of` 只从「虚/中」里取 TOP3，清单全是「强」就返回空数组 | 永远按 虚→中→强 排序取满 3 条，「强」给的是「先练成 90 秒版本」；前端在没有条目时也渲染一条状态说明，不再留空白卡片 |
| 事实清单只有 1 条，5 轮围着一句打转 | 模型把一个项目的 3 条要点压成 1 条 | 服务端按简历要点补齐到 4 条（`_fact_key` 去掉 `｜` 抬头后去重，不重复入库），`note` 里如实写补了几条 |
| 「没有可验证的结果数据」提示不消失 | 标记写死在渲染时的 HTML 里，`input` 不重判 | 提示条常驻 DOM，靠 `.bullet-block.no-result` 开关，输入时实时切换 |
| 390px 下 STAR 标签溢出卡片 | `.review-q` 缺 `min-width:0`，长题目把右侧挤出界 | 补 `min-width:0` + `overflow-wrap:anywhere`，标签 `flex-shrink:0`；560px 以下换行到下一排，`.review-detail` 左边距收窄 |
| 导出 DOCX 丢教育时间段 | 后端只读 `time`，外部存档可能写 `period` | `docgen._period_of` 兼容 `time/period/date/duration/range` 与 `start+end`；前端 `normalizeResume` 读入时把别名收敛成 `time` |
| STAR 四枚标签全灰，像「四项都缺」 | 模型没给 `star`，工具默认补成四个 `false` | `save_report` 允许 `star: null`；前端渲染成「STAR 未评」，提示里写明是没评而不是全缺 |
| 文案写「事实编号 E1–E6」 | 写死在 HTML 里 | 改成「E1、E2…」，开始面试时按真实清单条数写成 `E1–En` |
