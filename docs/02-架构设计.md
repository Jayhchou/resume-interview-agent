# 02 · 架构设计

> 本文回答：这个智能体由哪几块组成、每块的边界在哪、为什么这样切。

---

## 一、总体架构

采用「**薄壳厚芯**」的四层结构。专家只承担**入口与人设**，真正的能力沉淀在技能与知识库里。

```
┌─────────────────────────────────────────────────┐
│  入口层   专家：人设 / 意图路由 / 会话状态        │  ← 唯一，账号绑定
├─────────────────────────────────────────────────┤
│  能力层   技能：6 个可复用能力单元                │  ← 项目级，可 git 协作
├─────────────────────────────────────────────────┤
│  知识层   资料库：样本 / JD / 题库 / 方法论       │  ← 团队共同积累
├─────────────────────────────────────────────────┤
│  连接层   连接器：文档读取、外部数据（可选）      │  ← 个人授权
└─────────────────────────────────────────────────┘
```

### 1.1 为什么是「薄壳厚芯」

| 理由 | 说明 |
|---|---|
| **可协作** | 专家本体是云端配置、只读副本，团队无法共同编辑；技能与知识库是真实文件，能走分支与评审 |
| **可备份** | 专家只存在于托管人账号，一旦账号异常，能力层与知识层仍在仓库里 |
| **可复用** | 技能与知识库不绑定具体人设，将来换入口形态不必重做 |
| **可答辩** | 「功能模块说明」这一项需要清晰的模块边界，分层是最容易讲清的结构 |

## 二、入口层：专家设计

### 2.1 关键决策——单专家还是专家团？

| 方案 | 优势 | 代价 |
|---|---|---|
| **A. 单专家 + 多模式**（推荐） | 积分消耗低；链接唯一、演示稳定；状态连续（诊断完可直接进面试） | 角色区分靠提示词切换，人设跨度大 |
| B. 专家团（诊断官 / 面试官 / 教练） | 角色边界锐利，答辩时显得技术含量高 | 积分消耗为单专家 3—5 倍；演示需多次切换；托管人负担重 |

**决策：采用 A。** 触发改成 B 的条件：演示账号积分余额足以支撑 ≥10 次完整演示，且答辩时间允许切换三次场景。否则单专家是更稳的选择。

> 答辩要点：多角色不是靠多开专家实现的，而是靠**技能切换 + 会话状态机**实现的。这一点讲清楚，比堆专家更有说服力。

### 2.2 专家配置四要素

| 配置项 | 内容要点 | 常见错误 |
|---|---|---|
| 显示名称 | 中性、指向清晰、不含院校与姓名 | 「XX 大学求职助手」——直接违规 |
| 头像 | 无个人特征的图形 | 用真人照片或校徽 |
| 人设身份 | 是谁 + 有什么背景，落到具体年限与领域 | 「你是一个专业的简历专家」（空） |
| 擅长领域 | 明确写**做什么**与**不做什么** | 写成「什么都能帮」 |
| 提示词 | 工作流 + 输出格式 + 约束 + 示例 | 只写角色设定，不写流程 |

完整提示词真本见 [`../expert-prompt.md`](../expert-prompt.md)。

## 三、能力层：技能清单

技能是**单一职责、可组合**的能力单元。每一个技能对应一次明确的输入输出契约。

| # | 技能 | 职责 | 输入 | 输出 | 依赖知识 | 负责角色 |
|---|---|---|---|---|---|---|
| 1 | `jd-parse` | 把岗位描述拆成硬性要求、加分项、关键词 | JD 原文 | 结构化岗位卡 | JD 库 | 简历组 |
| 2 | `resume-parse` | 把简历拆成教育 / 经历 / 项目 / 技能四块 | 简历文本 | 结构化简历 | 无 | 简历组 |
| 3 | `resume-diagnose` | 四维打分并逐条给出原文定位 | 结构化简历 + 岗位卡 | 诊断报告 | 样本库、方法论 | 简历组 |
| 4 | `resume-rewrite` | 按岗位定向改写条目，只改表达不改事实 | 诊断报告 + 指定条目 | 改写对照表 | 术语表、样本库 | 简历组 |
| 5 | `interview-sim` | 按岗位出题并做至少 3 层追问 | 岗位卡 + 会话上下文 | 问答记录 | 题库 | 面试组 |
| 6 | `interview-review` | 把问答记录转成结构化复盘 | 问答记录 | 复盘报告 | 方法论 | 面试组 |

### 3.1 技能边界原则

1. **一个技能只做一件事。** 诊断不负责改写，改写不负责评分。混在一起会让输出两头都不深。
2. **技能之间只通过结构化数据衔接。** 上游输出必须落到固定字段，下游才可靠。
3. **每个技能自带拒答规则。** 例如 `resume-rewrite` 遇到「帮我编一段实习」必须拒绝并转劝导。
4. **技能内部不写人设。** 人设属于入口层，技能只写方法与约束，便于复用。

### 3.2 技能文件形态

```
skills/
└── resume-diagnose/
    ├── SKILL.md        职责、触发条件、输入输出契约、执行步骤
    ├── references/     评分细则、维度定义、范例
    └── scripts/        需要确定性计算时的脚本（如关键词覆盖率）
```

## 四、知识层：资料库构建

> 对应赛题必答项「知识库来源」。这里写的每一条，都必须是**真的存在于资料库里**的，答辩时会被追问。

### 4.1 知识库构成

| 分区 | 内容 | 来源 | 更新方式 |
|---|---|---|---|
| 简历样本库 | 好 / 中 / 差三档脱敏简历，标注扣分点 | 自建（禁止使用真实他人简历） | 团队提交 |
| 岗位卡库 | 按行业与岗位分层的 JD 结构化卡片 | 公开招聘信息整理 | 按批次补充 |
| 面试题库 | 行为面 / 项目深挖 / 技术面三类问题 | 公开面经归纳 + 自建 | 团队提交 |
| 方法论库 | STAR、量化表达、关键词覆盖、简历结构规范 | 公开方法论整理 | 稳定，少变 |
| 术语表 | 行业术语与同义表达映射 | 自建 | 按需 |

### 4.2 知识库的三条纪律

1. **来源可溯**：每份资料标注出处与整理人角色（不写真实姓名）。
2. **样本必须自造或深度脱敏**：这是隐私红线，也是匿名红线。
3. **宁少勿杂**：一份高质量样本胜过十份泛泛资料；知识库污染会直接放大成诊断错误。

### 4.3 知识库与技能的对应关系

技能是「怎么想」，知识库是「拿什么想」。同一技能配不同知识库，就能切换行业——这也是后续延展性的技术基础。

## 五、连接层：连接器

| 连接器 | 用途 | 必要性 | 风险 |
|---|---|---|---|
| 文档读取 | 直接读取 PDF / DOCX 简历 | 高 | 扫描件无法解析，需降级 |
| 表格读写 | 批量场景下导出诊断结果 | 中 | 无 |
| 招聘网站类 | 直接抓取 JD | 低 | 授权与合规风险，**MVP 不做** |

**原则：连接器只做「取数据」和「交付结果」，不承担推理。** 推理必须在技能层，否则不可复现、不可测试。

## 六、数据流

### 6.1 主链路

```
用户输入
   │
   ├─ 意图路由（入口层）
   │
   ├─[改简历]→ resume-parse → jd-parse → resume-diagnose → resume-rewrite
   │                                                              │
   │                                                              ↓
   │                                                        改写对照表
   │
   └─[练面试]→ jd-parse → interview-sim ⇄ (多轮追问) → interview-review
                                                              │
                                                              ↓
                                                        复盘报告
```

### 6.2 两种闭环

- **简历闭环**：诊断 → 改写 → 再诊断（分数变化即价值证明）
- **面试闭环**：出题 → 追问 → 复盘 → 针对薄弱项再练

两条闭环在「岗位卡」处共享同一个数据结构，因此用户可以先改简历再练面试，上下文不断。

## 七、交付与运维

### 7.1 交付形态

- **唯一入口**：托管人账号生成的专家分享链接
- 成员与评委通过链接召唤的是**副本**，不影响主配置
- 链接失效即作品不完整，因此：

| 风险 | 应对 |
|---|---|
| 误删专家 | 项目期间禁止删除；删除不可恢复 |
| 改名冲动 | 名称创建后不可修改，定名前须团队确认 |
| 托管人账号异常 | 凭据由 ≥2 人掌握；`expert-prompt.md` 为唯一还原依据 |
| 积分耗尽 | 调试集中在托管人账号，需预留演示额度 |

### 7.2 发布检查表

上线前逐项确认：

- [ ] 六个技能中 Must 项全部跑通
- [ ] 资料库已挂载且能被正确检索
- [ ] 三组演示提示词输出稳定（连续跑三次结果一致）
- [ ] 全部截图已脱敏
- [ ] 分享链接用另一个账号验证可打开
- [ ] `expert-prompt.md` 与平台配置一致
