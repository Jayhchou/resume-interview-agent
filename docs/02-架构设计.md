# 02 · 架构设计

> 本文回答：这个智能体由哪几块组成、每块的边界在哪、为什么这样切。

---

## 一、总体架构

采用「**薄壳厚芯**」的四层结构。专家只承担**入口与人设**，真正的能力沉淀在技能与知识库里。

```
┌─────────────────────────────────────────────────┐
│  入口层   专家：人设 / 意图路由 / 会话状态        │  ← 唯一，账号绑定
├─────────────────────────────────────────────────┤
│  能力层   技能：6 个可复用能力单元                │  ← 项目级，可 git 协作
├─────────────────────────────────────────────────┤
│  知识层   资料库：样本 / JD / 题库 / 方法论       │  ← 团队共同积累
├─────────────────────────────────────────────────┤
│  连接层   连接器：文档读取、外部数据（可选）      │  ← 个人授权
└─────────────────────────────────────────────────┘
```

### 1.1 为什么是「薄壳厚芯」

| 理由 | 说明 |
|---|---|
| **可协作** | 专家包是磁盘目录，人设、技能、素材全是真实文件，能走分支与评审；唯一不可并行的是「生成分享链接」这一步，它绑在托管人账号上 |
| **可备份** | 专家只存在于托管人账号，一旦账号异常，能力层与知识层仍在仓库里 |
| **可复用** | 技能与知识库不绑定具体人设，将来换入口形态不必重做 |
| **可答辩** | 「功能模块说明」这一项需要清晰的模块边界，分层是最容易讲清的结构 |

## 二、入口层：专家设计

### 2.1 关键决策——单专家还是专家团？

先说清两条**不成立**的理由，免得后面被自己的笔记误导：

- ~~积分消耗高~~：团队每个账号有独立额度，可用轮流分担调试开销；且官方口径是「通常 3—5 倍、不可按固定倍数估算」，不是硬约束。
- ~~专家团不能生成分享链接~~：已实测可以生成。赛题要的「一个可访问链接」两个方案都满足。

真正的判据只有一条——**交互形态**：

| 方案 | 交互形态 | 适配性 |
|---|---|---|
| **A. 单专家 + 双技能**（采用） | 一问一答，状态在同一会话内延续 | ✅ 模拟面试需要「记住上一句并顺着往下扎」，这是多轮实时交互 |
| B. 专家团（简历官 / 面试官 / 团长） | 团长拆任务 → 成员并行或依次执行 → 汇总输出 | ❌ 批处理结构，做不了多轮追问；且多出一个谁都不拥有的「团长」角色，运行时自行决定拆到什么粒度，演示不可控 |

**决策：采用 A。** 补充说明：专家团技术上并非做不到，而是每一轮问答都要过一遍团长重新编排，代价全在延迟与积分上，收益为零——因为面试的价值来自连续记忆，不来自多视角。

> 答辩要点（背下来）：**这两个模块是串行的实时交互，不是并行的多视角分工；专家团的优势在后者。** 我们用「一个专家 + 两个技能 + 显式状态文件」，把协作成本压到最低，把交互质量留住。
>
> 专家团的真实适用点：一份简历同时给 HR / 技术 / 业务三个视角**并行**审，团长汇总分歧。这是并行，不是串行——留作答辩时的对比案例，不进主线。


### 2.2 专家配置四要素

| 配置项 | 内容要点 | 常见错误 |
|---|---|---|
| 显示名称 | 中性、指向清晰、不含院校与姓名 | 「XX 大学求职助手」——直接违规 |
| 头像 | 无个人特征的图形 | 用真人照片或校徽 |
| 人设身份 | 是谁 + 有什么背景，落到具体年限与领域 | 「你是一个专业的简历专家」（空） |
| 擅长领域 | 明确写**做什么**与**不做什么** | 写成「什么都能帮」 |
| 提示词 | 工作流 + 输出格式 + 约束 + 示例 | 只写角色设定，不写流程 |

完整提示词真本见 [`../expert-prompt.md`](../expert-prompt.md)。

## 三、能力层：技能清单

**决策：两个技能，按模块切，一个专家同时挂载。**

| # | 技能 | 职责 | 输入 | 输出 | 素材（references） | 负责角色 |
|---|---|---|---|---|---|---|
| 1 | `resume-coach` | 解析简历 → 五维诊断 → 定向改写；只改表达不改事实 | 简历文本 + 目标 JD（可选） | 五维评分 + 逐条扣分定位 + 改写对照表 | 案例库、改写句式 | 简历组 |
| 2 | `interview-coach` | 按场景与岗位出题 → 逐层追问 → 结构化复盘 | 事实清单 + 场景 + 岗位 | 问答记录 + 复盘报告 | 面试题库、评分量规 | 面试组 |

挂载方式（`plugin.json`）：

```json
"skills": ["./skills/resume-coach", "./skills/interview-coach"]
```

### 3.1 为什么是两个，不是六个也不是一个

| 方案 | 判断 |
|---|---|
| 拆成六个（parse / diagnose / rewrite / sim / review…） | ❌ 把「流程步骤」当成「技能边界」。解析、诊断、改写是同一句话触发的连续动作，拆开后每个都很薄，且互相要传递半成品 |
| 只做一个（当前测试包的形态） | ❌ 两人必须同时改同一个 `SKILL.md`，冲突无法消除；两种口吻（耐心改写 / 施压追问）混在一个提示词里会串味 |
| **按模块拆两个** | ✅ 两个模块有**独立的触发条件**（「帮我看看简历」vs「我想模拟面试」）、独立口吻、独立素材、独立负责人 |

**拆分标准只有一条：用户会不会单独发起这个请求。** 会，就独立成技能；不会（只是流程中的一步），就留在技能内部。

### 3.2 技能边界原则

1. **技能之间只通过结构化数据衔接。** 交接物是「候选人事实清单」，定义见 [`03-逻辑梳理.md`](03-逻辑梳理.md) 第四节。
2. **技能内部不写人设。** 人设属于入口层，技能只写方法与约束。
3. **每个技能自带拒答规则。** 遇到「帮我编一段实习」必须拒绝并转劝导。
4. **一个技能只做一件事。** 诊断不负责改写，追问不负责评分。

### 3.3 技能文件形态

```
skills/
├── resume-coach/
│   ├── SKILL.md
│   └── references/
│       ├── resume-benchmark-library.md   案例库 + 对标检查表
│       └── resume-rewrite-patterns.md    改写句式、动词替换、量化清单
└── interview-coach/
    ├── SKILL.md
    └── references/
        ├── interview-question-bank.md    分场景题库 + 追问链
        └── scoring-rubric.md             五维评分量规 + 各场景权重
```

素材（references）挂在各自技能下，**一份文件一个 owner**，两人各占一列，git 上零冲突。

## 四、知识层：资料库构建

> 对应赛题必答项「知识库来源」。这里写的每一条，都必须是**真的存在于资料库里**的，答辩时会被追问。

### 4.1 知识库构成

| 分区 | 内容 | 来源 | 更新方式 |
|---|---|---|---|
| 简历样本库 | 好 / 中 / 差三档脱敏简历，标注扣分点 | 自建（禁止使用真实他人简历） | 团队提交 |
| 岗位卡库 | 按行业与岗位分层的 JD 结构化卡片 | 公开招聘信息整理 | 按批次补充 |
| 面试题库 | 行为面 / 项目深挖 / 技术面三类问题 | 公开面经归纳 + 自建 | 团队提交 |
| 方法论库 | STAR、量化表达、关键词覆盖、简历结构规范 | 公开方法论整理 | 稳定，少变 |
| 术语表 | 行业术语与同义表达映射 | 自建 | 按需 |

### 4.2 知识库的三条纪律

1. **来源可溯**：每份资料标注出处与整理人角色（不写真实姓名）。
2. **样本必须自造或深度脱敏**：这是隐私红线，也是匿名红线。
3. **宁少勿杂**：一份高质量样本胜过十份泛泛资料；知识库污染会直接放大成诊断错误。

### 4.3 知识库与技能的对应关系

技能是「怎么想」，知识库是「拿什么想」。同一技能配不同知识库，就能切换行业——这也是后续延展性的技术基础。

## 五、连接层：连接器

| 连接器 | 用途 | 必要性 | 风险 |
|---|---|---|---|
| 文档读取 | 直接读取 PDF / DOCX 简历 | 高 | 扫描件无法解析，需降级 |
| 表格读写 | 批量场景下导出诊断结果 | 中 | 无 |
| 招聘网站类 | 直接抓取 JD | 低 | 授权与合规风险，**MVP 不做** |

**原则：连接器只做「取数据」和「交付结果」，不承担推理。** 推理必须在技能层，否则不可复现、不可测试。

## 六、数据流

### 6.1 主链路

```
用户输入
   │
   ├─ 意图路由（入口层，判断进哪个技能）
   │
   ├─[改简历]→ resume-coach
   │              解析 → 五维诊断 → 定向改写
   │                    └──→ 产出【候选人事实清单】
   │
   └─[练面试]→ interview-coach
                  读入【候选人事实清单】→ 按场景追问 → 复盘
                          └──→ 回填新的证据缺口
```

### 6.2 两种闭环

- **简历闭环**：诊断 → 改写 → 再诊断（五维分数变化即价值证明）
- **面试闭环**：按清单追问 → 复盘 → 缺口回填 → 下一轮只练薄弱项

两条闭环共享**同一个数据结构：候选人事实清单**（定义见 `03-逻辑梳理.md` 第四节）。它不是岗位卡——岗位卡来自 JD，事实清单来自简历诊断的产物。用户先改简历再练面试时，上下文正是靠它延续，而不是靠会话记忆。

## 七、交付与运维

### 7.1 交付形态

- **唯一入口**：托管人账号生成的专家分享链接
- 成员与评委通过链接召唤的是**副本**，不影响主配置
- 链接失效即作品不完整，因此：

| 风险 | 应对 |
|---|---|
| 误删专家 | 项目期间禁止删除；删除不可恢复 |
| 改名冲动 | 名称创建后不可修改，定名前须团队确认 |
| 托管人账号异常 | 凭据由 ≥2 人掌握；`expert-prompt.md` 为唯一还原依据 |
| 积分耗尽 | 调试集中在托管人账号，需预留演示额度 |

### 7.2 发布检查表

上线前逐项确认：

- [ ] 两个技能（`resume-coach` / `interview-coach`）各自跑通，且能通过事实清单衔接
- [ ] 资料库已挂载且能被正确检索
- [ ] 三组演示提示词输出稳定（连续跑三次结果一致）
- [ ] 全部截图已脱敏
- [ ] 分享链接用另一个账号验证可打开
- [ ] `expert-prompt.md` 与平台配置一致
